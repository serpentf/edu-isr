# Методы ручного тестирования

## Цель урока

Разобрать семь методов ручного тестирования и понять, когда применять каждый.

## Исследовательское тестирование (exploratory)

Одновременное **изучение** продукта, **проектирование** и **выполнение** тестов. Тестировщик не идёт по готовому сценарию: каждое следующее действие он выбирает по результатам предыдущего.

Чтобы исследование не превратилось в хаотичное «потыкать», его организуют **сессиями по 60–90 минут** с чёткой целью — **чартером**.

> **Пример чартера.** «Исследовать оформление заказа с промокодами, чтобы найти ошибки в расчёте итоговой суммы».

По итогам сессии фиксируют: что проверено, какие дефекты найдены, какие вопросы и идеи появились.

## Ad-hoc (свободное) тестирование

Неформальные проверки **без документации**, на основе опыта и интуиции. От исследовательского отличается отсутствием структуры: нет чартера, нет ограничения по времени, результаты обычно не фиксируются, кроме найденных багов.

## Сценарное тестирование (scripted)

Строгое следование **заранее написанным тест-кейсам**: предусловия, шаги, ожидаемый результат. Результаты воспроизводимы: разные люди выполнят проверку одинаково. Сценарные тест-кейсы — главные кандидаты на будущую автоматизацию.

## Smoke-тестирование

Быстрая проверка **критических функций**: «запускается ли система вообще». Сборка открывается, пользователь может войти, главная страница загружается, основной сценарий проходит.

Если smoke не пройден, глубокое тестирование не начинают: сборку возвращают разработчикам.

## Санитарное тестирование (sanity)

**Узкая** проверка **конкретной функции** после небольшого исправления: убедиться, что исправление работает и рядом ничего очевидно не сломалось.

| | Smoke | Sanity |
|---|-------|--------|
| Охват | Широкий, но поверхностный: все критические функции | Узкий, но глубже: одна функция |
| Когда | На каждой новой сборке | После точечного исправления |
| Вопрос | «Система вообще работает?» | «Вот это исправление работает?» |

## Приёмочное тестирование (UAT)

User Acceptance Testing выполняет **заказчик или представители бизнеса**. Его задача — подтвердить, что продукт решает их задачи. Варианты:

- **Альфа-тестирование** — проводится внутри компании-разработчика, до выхода к внешним пользователям.
- **Бета-тестирование** — проводится ограниченным кругом реальных внешних пользователей.

## Юзабилити-тестирование

**Наблюдение за реальными пользователями** при выполнении типовых задач. Пользователю дают задание («купите чайник с доставкой на завтра») и смотрят, где он сомневается, ошибается и тратит лишнее время.

## Сводная таблица

| Метод | Документация | Кто выполняет | Главная цель |
|-------|-------------|---------------|--------------|
| Исследовательское | Чартер, заметки сессии | Тестировщик | Найти неочевидные дефекты |
| Ad-hoc | Нет | Тестировщик | Быстро найти очевидные проблемы |
| Сценарное | Тест-кейсы | Тестировщик | Воспроизводимая проверка требований |
| Smoke | Короткий чек-лист | Тестировщик | Решить, годится ли сборка для тестирования |
| Sanity | Короткий чек-лист | Тестировщик | Подтвердить точечное исправление |
| UAT | Бизнес-сценарии | Заказчик, бизнес | Принять продукт |
| Юзабилити | Сценарии задач | Реальные пользователи | Оценить удобство |

## Главное

- Исследовательское тестирование структурируется сессиями 60–90 минут с чартером.
- Smoke — широкая поверхностная проверка сборки, sanity — узкая проверка исправления.
- UAT выполняет заказчик, юзабилити-тесты — реальные пользователи.
