# Жизненный цикл дефекта и баг-репорт

## Цель урока

Изучить статусы, через которые проходит дефект, и научиться писать баг-репорт, по которому ошибку можно воспроизвести с первого раза.

## Жизненный цикл дефекта

```
Новый → Назначен → В работе → Исправлен → На проверке → Закрыт
                                               │
                                               └─ проверка не прошла → Переоткрыт → В работе
```

| Статус | Кто действует | Что происходит |
|--------|---------------|----------------|
| **Новый** | Тестировщик | Дефект зарегистрирован |
| **Назначен** | Руководитель, тимлид | Выбран ответственный разработчик |
| **В работе** | Разработчик | Идёт исправление |
| **Исправлен** | Разработчик | Исправление готово и попало в сборку |
| **На проверке** | Тестировщик | Повторная проверка исправления |
| **Закрыт** | Тестировщик | Исправление подтверждено |

Если проверка не прошла, **дефект переоткрывается** и возвращается разработчику. После закрытия полезно выполнить sanity-проверку соседней функциональности (модуль 2).

## Хороший баг-репорт

Баг-репорт пишется для разработчика, который не видел ошибку своими глазами. Его задача — **воспроизвести дефект без дополнительных вопросов**.

| Поле | Содержание |
|------|-----------|
| **Заголовок** | Кратко: что, где, при каких условиях |
| **Шаги воспроизведения** | Пронумерованные, конкретные, с тестовыми данными |
| **Ожидаемый результат** | Что должно было произойти (по требованиям) |
| **Фактический результат** | Что произошло на самом деле |
| **Окружение** | Версия сборки, браузер, ОС, устройство |
| **Серьёзность и приоритет** | См. ниже |
| **Вложения** | Скриншоты, видео, логи |

### Пример

> **Заголовок:** Корзина: промокод SALE10 применяется повторно при обновлении страницы
>
> **Шаги:**
> 1. Добавить в корзину товар стоимостью 1000 ₽.
> 2. Ввести промокод SALE10 и нажать «Применить».
> 3. Обновить страницу (F5).
>
> **Ожидаемый результат:** итого 900 ₽.
> **Фактический результат:** итого 810 ₽, скидка применилась второй раз.
> **Окружение:** сборка 2.14.0, Chrome 129, Windows 11.
> **Серьёзность:** критическая. **Приоритет:** высокий.
> **Вложения:** видео воспроизведения, лог запроса `/api/cart`.

### Типичные ошибки

- Заголовок «Не работает корзина» — непонятно, что именно.
- Шаги «Добавить товар и применить скидку» — какой товар? какой промокод?
- Нет ожидаемого результата — разработчик может не считать поведение ошибкой.
- Несколько дефектов в одном репорте — их невозможно закрыть по отдельности.

## Серьёзность и приоритет

- **Серьёзность (severity)** — насколько дефект влияет на работу системы. Оценивает тестировщик.
- **Приоритет (priority)** — насколько срочно его исправлять. Определяет менеджер или владелец продукта.

Это разные оси. Опечатка в названии компании на главной странице — низкая серьёзность, но высокий приоритет. Падение редкого отчёта, которым пользуется один сотрудник раз в год, — высокая серьёзность, но приоритет может быть низким.

## Главное

- Статусы: Новый → Назначен → В работе → Исправлен → На проверке → Закрыт; при неудачной проверке — переоткрытие.
- Баг-репорт должен позволять воспроизвести дефект без вопросов.
- Серьёзность — про влияние, приоритет — про срочность.

## Вопросы для самопроверки

2. Чем ожидаемый результат отличается от фактического и зачем указывать оба?
3. Приведите пример дефекта с высокой серьёзностью и низким приоритетом.
