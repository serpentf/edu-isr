# Выбор стратегии

## Цель урока

Научиться подбирать соотношение ручного и автоматизированного тестирования под ситуацию проекта и тип функционала.

## Принцип

> Оптимальная стратегия почти всегда **смешанная**: автоматизируется **повторяющееся и стабильное**, вручную проверяется **новое и визуальное**.

## Стратегия по ситуации проекта

| Ситуация | Рекомендуемый подход | Почему |
|----------|----------------------|--------|
| Стартап с меняющимися требованиями | Ручное + модульные тесты от разработчиков | UI-автотесты пришлось бы постоянно переписывать, а модульные тесты дёшевы и страхуют логику |
| Оценка удобства интерфейса | Только ручное | Удобство оценивает только человек |
| Разовый выпуск (лендинг) | Ручное | Автоматизация не успеет окупиться |
| Долгосрочный проект с частыми релизами | Автоматизация регрессии в CI/CD | Много повторных прогонов — быстрая окупаемость |
| Тысячи однотипных проверок (валидация полей) | Автоматизация, data-driven тесты | Человек устанет и ошибётся, скрипт — нет |
| Проверка производительности под нагрузкой | Только автоматизация | Тысячи пользователей вручную не сымитировать |

**Data-driven тест** — один автотест, который выполняется многократно на таблице входных данных и ожидаемых результатов. Например, таблица классов эквивалентности для поля «Возраст» из модуля 5 превращается в один параметризованный тест:

```python
@pytest.mark.parametrize("age, accepted", [
    ("17", False), ("18", True), ("19", True),
    ("64", True), ("65", True), ("66", False),
    ("абв", False), ("", False),
])
def test_age_validation(age, accepted):
    assert validate_age(age) == accepted
```

## Стратегия по типу функционала

Внутри одного проекта разные части требуют разного подхода:

1. **Критический функционал → автоматизация + ручной обзор.** Автотесты страхуют от регрессии на каждом коммите, человек периодически смотрит на сценарий целиком.
2. **Новые фичи → сначала ручное исследовательское тестирование, автотесты — после стабилизации.**
3. **Стабильные сценарии (логин, регистрация, платежи) → автоматизация.**
4. **UI/UX-элементы → ручное**, при необходимости дополняется визуальным регрессионным тестированием.

Обратите внимание на пункт 2: функциональность **переходит** из ручной зоны в автоматизированную по мере созревания. Стратегия — это не разовое решение, а процесс.

## Главное

- Стратегия почти всегда смешанная.
- Выбор зависит от ситуации проекта и типа функционала.
- Новое тестируется вручную и автоматизируется после стабилизации.
