# Внедрение автоматизации и метрики

## Цель урока

Освоить пошаговый порядок внедрения автоматизации и метрики, по которым можно судить о качестве тестирования.

## Порядок внедрения автоматизации

### 1. Наладить ручной процесс и описать регрессионные тест-кейсы

Нельзя автоматизировать то, что не описано. Если команда сама не знает, что проверять перед релизом, автотесты будут проверять случайный набор сценариев.

### 2. Выбрать кандидатов

Хороший кандидат на автоматизацию одновременно:

- **часто повторяется** — каждый релиз или каждый коммит;
- **стабилен** — функциональность не меняется от релиза к релизу;
- **критичен для бизнеса** — деньги, данные, безопасность, ключевой пользовательский путь.

### 3. Выбрать инструменты под стек и навыки команды

Критерии из модуля 6: технологии продукта, квалификация команды, бюджет, интеграция с CI.

### 4. Начать с модульных и API-тестов, затем добавить ключевые UI-сценарии

Порядок задаёт пирамида тестирования (модуль 3). Начав с UI, команда быстро построит «рожок мороженого».

### 5. Подключить запуск в CI и настроить отчёты

Автотесты, которые запускают вручную «когда вспомнят», почти не приносят пользы. Ценность появляется, когда тесты запускаются на каждый коммит и работает quality gate (модуль 7).

### 6. Регулярно чистить нестабильные и устаревшие тесты

Набор автотестов — это код, который требует поддержки. Flaky-тесты нужно исправлять или удалять, тесты удалённой функциональности — удалять. Иначе команда перестанет доверять результатам.

## Метрики качества тестирования

| Метрика | Что показывает | На что обратить внимание |
|---------|----------------|--------------------------|
| **Покрытие кода тестами** | Какая доля строк и ветвлений выполняется тестами | Высокое покрытие не гарантирует качество: тест без проверок тоже «покрывает» код |
| **Покрытие требований** | Для какой доли требований есть тесты | Показывает непроверенные функции |
| **Доля дефектов, пропущенных в продакшен** | Сколько дефектов нашли пользователи, а не команда | Главный показатель эффективности тестирования |
| **Доля нестабильных тестов** | Сколько тестов flaky | Растёт — доверие к автоматизации падает |
| **Время полного регрессионного прогона** | Как быстро команда узнаёт о проблемах | Растёт — обратная связь замедляется, пора распараллеливать или пересматривать пирамиду |

Метрики полезно смотреть **в динамике** и **вместе**. Например, если покрытие кода растёт, а доля пропущенных дефектов не падает, возможно, тесты пишутся ради цифры, а не ради проверок.

## Главное

- Шесть шагов: ручной процесс → кандидаты → инструменты → unit и API → CI → чистка.
- Кандидат на автоматизацию: частый, стабильный, критичный.
- Главная метрика — доля дефектов, пропущенных в продакшен.

## Вопросы для самопроверки

1. Почему внедрение автоматизации начинается с налаживания ручного процесса?
2. Сценарий выполняется каждый релиз, но интерфейс меняется каждый спринт. Хороший ли это кандидат на UI-автоматизацию?
3. Почему 100% покрытия кода не означает отсутствия дефектов?
