# Тестирование API

## Цель урока

Понять, из чего состоят запрос и ответ HTTP API, что именно в них проверять и как выглядит автотест для API.

## Что такое API и почему его тестируют отдельно

**API** (Application Programming Interface) — программный интерфейс, через который фронтенд, мобильное приложение и другие сервисы общаются с сервером. Когда вы нажимаете «Оформить заказ», страница отправляет на сервер HTTP-запрос и показывает то, что вернулось в ответе.

API-тесты занимают **середину пирамиды тестирования** (модуль 3). Они проверяют бизнес-логику без графического интерфейса, поэтому:

- работают **быстрее** UI-тестов: не нужен браузер, не нужно ждать отрисовки;
- **стабильнее**: не ломаются от того, что кнопку перекрасили или переместили;
- **точнее локализуют** ошибку: если API вернул неверную сумму заказа, проблема на сервере, а не в вёрстке.

## Анатомия запроса

| Часть | Пример | Зачем |
|-------|--------|-------|
| **Метод** | `GET`, `POST`, `PUT`, `DELETE` | Что сделать: получить, создать, изменить, удалить |
| **Путь** | `/products/1` | С каким ресурсом |
| **Заголовки** | `Authorization: Bearer secret-token` | Служебные данные: кто отправляет, в каком формате |
| **Тело** | `{ "productId": 1, "quantity": 2 }` | Данные для создания или изменения (у `POST` и `PUT`) |

## Анатомия ответа

Ответ состоит из **кода статуса** и **тела**, обычно в формате JSON. Код статуса — первое, что проверяет любой API-тест:

| Код | Значение | Когда |
|-----|----------|-------|
| **200** OK | Успех | Данные получены |
| **201** Created | Создано | `POST` успешно создал ресурс |
| **400** Bad Request | Ошибка в запросе | Не прошла валидация: пустое поле, отрицательное количество |
| **401** Unauthorized | Нет авторизации | Нет токена или он неверный |
| **403** Forbidden | Нет прав | Токен верный, но действие запрещено |
| **404** Not Found | Не найдено | Ресурса с таким id нет |
| **500** Internal Server Error | Ошибка сервера | Сервер упал. Для любого запроса это дефект |

## Что проверять в API

1. **Код статуса.** Успешный запрос — 2xx, ошибка клиента — 4xx, и именно тот код, что описан в документации.
2. **Тело ответа.** Правильные значения, все обязательные поля на месте.
3. **Типы данных.** Цена `2500` и цена `"2500"` — разные вещи: фронтенд, который складывает цены, получит `"2500" + 400 = "2500400"`.
4. **Негативные сценарии.** Несуществующий id, некорректные данные, граничные значения (модуль 5).
5. **Авторизация.** Без токена защищённые операции недоступны.
6. **Побочные эффекты.** После `POST` созданный объект действительно появляется в `GET`, а остаток на складе уменьшается.

## Как выглядит автотест для API

В практических заданиях есть объект `api`. Он отправляет запрос к демо-серверу и возвращает ответ `{ status, body }`. Тест строится по той же схеме [AAA](../../03-automated-testing/lessons/04-test-structure.md) (модуль 3):

```js
test('несуществующий товар возвращает 404', () => {
  // Arrange: товара с id 999 в каталоге нет
  const missingId = 999;

  // Act
  const res = api.get(`/products/${missingId}`);

  // Assert
  expect(res.status).toBe(404);
  expect(res.body.error).toBe('Product not found');
});

test('без токена заказ не создаётся', () => {
  const res = api.post('/orders', { productId: 1, quantity: 1 });
  expect(res.status).toBe(401);
});

test('с токеном заказ создаётся', () => {
  const auth = { headers: { Authorization: 'Bearer secret-token' } };
  const res = api.post('/orders', { productId: 1, quantity: 2 }, auth);
  expect(res.status).toBe(201);
  expect(res.body.total).toBe(5000);
});
```

Методы клиента: `api.get(path, options)`, `api.post(path, body, options)`, `api.put(path, body, options)`, `api.delete(path, options)`. В `options` передаются заголовки: `{ headers: { Authorization: '...' } }`.

**Каждый тест начинается с чистых данных.** Перед каждым тестом сервер создаётся заново, поэтому тесты не зависят друг от друга и от порядка запуска. Это то же требование, что и к flaky-тестам из модуля 3: общее изменяемое состояние между тестами — частая причина нестабильности.

## Как это выглядит в реальном проекте

В учебных заданиях запросы выполняются мгновенно и синхронно. В реальном проекте запросы идут по сети, поэтому тесты асинхронные. Например, на Jest с библиотекой supertest:

```js
const request = require('supertest');
const app = require('../src/app');

test('несуществующий товар возвращает 404', async () => {
  const res = await request(app).get('/api/products/999');
  expect(res.status).toBe(404);
});
```

Идеи те же: запрос, проверка статуса, проверка тела. Меняются только инструменты: REST Assured в Java, `requests` + PyTest в Python, Postman + Newman без программирования (урок 3).

## От ручной проверки к автотесту

На странице практических заданий есть **API-консоль** — упрощённый Postman. Отправьте запрос вручную, посмотрите на ответ и нажмите **«Добавить как тест»**: консоль превратит запрос и ответ в готовый автотест. Ровно так часто и работают тестировщики: сначала исследуют API вручную, затем закрепляют найденные сценарии автотестами.

## Главное

- API-тесты быстрее и стабильнее UI-тестов и составляют середину пирамиды.
- Проверяйте статус, тело, типы данных, ошибки, авторизацию и побочные эффекты.
- Каждый тест должен начинаться с известного состояния данных.
