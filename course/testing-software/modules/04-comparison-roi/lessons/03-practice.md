# Практика: расчёт точки безубыточности

## Задание

Для каждого проекта рассчитайте точку безубыточности N, переведите её в календарное время и дайте рекомендацию: автоматизировать регрессию или нет.

| Проект | Ручной прогон | Разработка автотестов | Поддержка на прогон | Частота релизов |
|--------|---------------|-----------------------|---------------------|-----------------|
| A. Интернет-банк | 10 ч | 60 ч | 1 ч | Раз в 2 недели |
| B. Внутренний справочник | 4 ч | 50 ч | 3 ч | Раз в месяц |
| C. Приложение с еженедельным редизайном | 3 ч | 40 ч | 3,5 ч | Раз в неделю |

Затем рассчитайте N для **своего** проекта (или придуманного): оцените часы, выпишите допущения и сформулируйте рекомендацию.

## Критерии оценки

| Критерий | Баллы |
|----------|-------|
| Верно рассчитано N для проектов A–C | 3 |
| N переведено в календарное время | 2 |
| Рекомендации обоснованы | 3 |
| Расчёт для собственного проекта с допущениями | 2 |
| **Итого** | **10** |

## Ответы для самопроверки

<details>
<summary>Показать ответы</summary>

**A.** N = 60 / (10 − 1) ≈ 6,7 → **7 прогонов** ≈ 14 недель, примерно 3,5 месяца. Интернет-банк — долгоживущий и критичный продукт, автоматизация оправдана.

**B.** N = 50 / (4 − 3) = **50 прогонов** ≈ 50 месяцев, больше 4 лет. Не окупится: ручной прогон дешёвый, а поддержка почти такая же дорогая. Оставить ручную регрессию по чек-листу.

**C.** Знаменатель 3 − 3,5 < 0: каждый автоматический прогон дороже ручного, **автоматизация не окупится никогда**. Причина — нестабильный UI. Стоит автоматизировать модульные и API-проверки, которые от редизайна не зависят, а UI проверять вручную.

</details>
